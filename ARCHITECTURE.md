# UVO: Unnamed Visual Odometry / SLAM
## Повна системна архітектура та технічний пайплайн (From Zero to Hero)

---

## 1. Вступ та філософія UVO

**UVO (Unnamed Visual Odometry / SLAM)** — це модульна, метрично-орієнтована система просторової орієнтації нового покоління, створена для роботи на автономних наземних платформах (UGV), безпілотниках (UAV) та пристроях Edge AI (NVIDIA Jetson Orin / x86 з RTX).

### Чому назріла потреба нового SLAM?
Класичні монокулярні системи (ORB-SLAM3, DSO) та нейромережеві моделі першої хвилі (DPVO, DROID-SLAM, 2021–2023) мають критичні обмеження:
1. **Масштабна невизначеність (Scale Ambiguity):** Монокулярна камера фізично не бачить абсолютних метрів без додаткових датчиків або метричних пріорів. У DPVO масштаб плаває або накопичує дрейф.
2. **Технічний борг та закритість:** Залежність від старих специфічних C++/CUDA кернелів (як `cuda_corr`, `cuda_ba`, `lietorch`), які важко портувати під нові архітектури GPU (NVIDIA Blackwell, RTX 50, нові версії JetPack) та неможливо скомпілювати в чистий TensorRT / ONNX.
3. **Крихкість на польових ландшафтах:** Класичні кутові детектори (FAST/ORB) та локальні 8x8 патчі сліпнуть на траві, піску, однорідній дорозі чи при різкому освітленні.

**Філософія UVO:**
* **Модульність (Plug-and-Play):** Кожен рівень (фронтенд, метрика, оптимізатор, замикання петель) відділений чітким інтерфейсом (Abstract Base Class). Будь-яку нейромережу чи алгоритм можна замінити за 10 хвилин.
* **Metric-First:** Метричний масштаб із фундаментних моделей (Metric3D v2) не накладається після одометрії, а є повноцінним учасником оптимізації у фактор-графі.
* **Edge-Ready:** Усі нейромережеві компоненти підбираються з розрахунком на прямий експорт у TensorRT (FP16/INT8) для стабільних 30–60+ FPS на Jetson Orin.

## 2. Порівняльний аналіз: Класичний SLAM vs Архітектура UVO

| Компонент / Задача | Класичний монокулярний SLAM (ORB-SLAM3 / DSO) | Нейромережевий DPVO (2022) | Нова архітектура UVO (2026) |
| :--- | :--- | :--- | :--- |
| **Вилучення ознак** | Рукописні детектори (ORB, FAST, BRIEF) | Згорткові карти (F-Net, I-Net) + 8x8 патчі | **XFeat (CVPR 2024)** або адаптивний трансформерний фронтенд |
| **Матчинг / Трекінг** | Епіполярний пошук дескрипторів + оптичний потік | Рекурентний GRU оновлювач (Optical Cost Volume) | **Напівщільний XFeat + LightGlue / Flash-Flow** |
| **Метричний масштаб** | Відсутній (Scale = 1.0, або дрейфує Sim(3)) | Проективний (дрейфує, вимагає зовнішнього калібрування) | **Метричний пріор із Metric3D v2 прямо у фактор-графі** |
| **Динамічні об'єкти** | Звичайний RANSAC (часто збоїть на машинах/людях) | Спроби маскування на основі коваріації | **Семантична + геометрична фільтрація руху на рівні фіч** |
| **Бекенд (Оптимізація)** | g2o / Ceres (CPU, блокуючий BA) | Кастомний `cuda_ba` (CUDA C++, жорсткі розміри) | **Диференційований Factor Graph (Theseus / SymForce)** |
| **Замикання петель** | DBoW2/3 (мішок слів, часто плутає траву/кущі) | Відсутнє або примітивний BoW | **DINOv2 / AnyLoc (VPR) + XFeat/LightGlue verification** |
| **Експорт в Edge/TRT** | Неможливий (суміш C++ та евристик) | Майже неможливий через GRU/Lietorch | **100% сумісний із TensorRT, FP16/INT8** |

## 3. Як працює класичний монокулярний SLAM (Покроково)

Щоб зрозуміти інновації UVO, розберемо канонічний цикл класичного SLAM:

1. **Ініціалізація (Кадри 0 та 1):**
   * Знаходяться кути (FAST/ORB).
   * Рахується матриця гомографії (H) для площин або фундаментальна/суттєва матриця (F/E) для 3D сцени за допомогою 8-точкового або 5-точкового алгоритму з RANSAC.
   * Тріангулюються перші 3D точки. Масштаб обирається випадково (наприклад, середня глибина = 1 метр).
2. **Трекінг кадр-до-кадру (Front-End):**
   * На кожному новому кадрі шукаються відповідності з попереднім.
   * Вирішується задача **PnP (Perspective-n-Point)**: за відомими 3D точками у просторі та їх 2D проекціями на матриці знаходиться нова поза камери (R, t).
3. **Ключові кадри (Keyframing):**
   * Якщо камера відійшла достатньо далеко або відсоток спільних точок упав нижче порогу (наприклад, < 65%), створюється Keyframe.
4. **Локальна оптимізація (Local Bundle Adjustment):**
   * На вікні з останніх N ключових кадрів мінімізується сумарна похибка репроекції:
     `Похибка = Сума || x_ij - Project(K, R_i, t_i, P_j) ||^2`
   * Використовується метод Левенберга-Марквардта. Старі кадри маргіналізуються через доповнення Шура.
5. **Loop Closure (Замикання петель):**
   * Перевіряється глобальна база візуальних слів (DBoW). Якщо знайдено схоже старе місце, оцінюється 7-параметрична трансформація Sim(3) (обертання, зсув, масштаб) і запускається глобальна корекція графу поз (Pose Graph Optimization).

**Головний недолік класики:** якщо під колесами однорідна трава, сніг чи рілля — детекторам ні за що зачепитися, трекінг зривається, а масштаб розвалюється.

## 4. Архітектура нового UVO (Детальний пайплайн "От і До")

Система UVO побудована як **конвеєр із 4 незалежних асинхронних контурів**, які обмінюються даними через спільний стан пам'яті (Shared State / Ring Buffers):

```
                       [ ВХІДНИЙ КАДР ]
                              │
                              ▼
┌───────────────────────────────────────────────────────────────┐
│ КОНТУР 0: Передобробка та фільтрація (Pre-processing)          │
│ • Geometric Undistortion (GPU Remap)                          │
│ • Dynamic Masking (відсікання людей, машин, трави під бампером)│
└─────────────────────────────┬─────────────────────────────────┘
                              │ Очищений RGB кадр
                              ▼
┌───────────────────────────────────────────────────────────────┐
│ КОНТУР 1: Швидкісний трекер одометрії (Front-End, 50-100 FPS) │
│ • Видобуток напівщільних фіч (XFeat Backbone)                │
│ • Каскадний швидкий трекінг відповідностей (Temporal Matcher) │
│ • Миттєва оцінка руху: Motion Prior + Differentiable PnP      │
│ • Детектор вибору ключового кадру (Keyframe Trigger)          │
└─────────────────────────────┬─────────────────────────────────┘
                              │ Новий Keyframe (Кадр + Фічі)
                              ▼
┌───────────────────────────────────────────────────────────────┐
│ КОНТУР 2: Метричний кондиціонер геометрії (Async, 10-15 FPS)  │
│ • Фундаментна нейромережа глибини (Metric3D v2)               │
│ • Генерація карти канонічної глибини Z_metric та нормалей N   │
│ • Оцінка невизначеності глибини (Depth Uncertainty Map)       │
│ • Розрахунок пріору площини руху (Ground Plane Prior)         │
└─────────────────────────────┬─────────────────────────────────┘
                              │ Метричні зв'язки (Metric Constraints)
                              ▼
┌───────────────────────────────────────────────────────────────┐
│ КОНТУР 3: Метричний фактор-граф (Local Factor Graph, 20-30 FPS)│
│ • Sliding Window оптимізація (вікно з N кадрів)              │
│ • Фактор 1: Репроекція візуальних точок (Visual Residual)     │
│ • Фактор 2: Метрична узгодженість глибини (Metric Residual)   │
│ • Фактор 3: Фіксація калібрувального калібру (Gauge Fix)     │
│ • Фактор 4: (Опційно) Преінтеграція IMU                       │
│ • Маргіналізація старих станів (Theseus / LM Solver)          │
└─────────────────────────────┬─────────────────────────────────┘
                              │ Свіжі згладжені пози
                              ▼
┌───────────────────────────────────────────────────────────────┐
│ КОНТУР 4: Глобальне замикання петель (Loop Closure, Sub-Hz)   │
│ • Глобальний дескриптор місця (DINOv2 / AnyLoc VPR)           │
│ • Топологічний пошук кандидатів у радіусі та за часом         │
│ • Жорстка 3D-2D верифікація (LightGlue / RANSAC)              │
│ • Глобальна оптимізація графу поз SE(3) (PGO)                 │
└───────────────────────────────────────────────────────────────┘
```

## 5. Детальний опис модулів, бібліотек та технологій (З варіантами заміни)

Усі компоненти спроєктовані за принципом слабкої зв'язності (Decoupled Architecture). Ви завжди знаєте, де закінчується інтерфейс одного модуля і починається інший.

---

### Модуль 1: Фронтенд-трекер (Front-End Tracking Engine)

* **Що робить:** Бере потік кадрів високої частоти (30–60 кадрів/сек), витягує характерні точки та обчислює між-кадровий зсув камери без очікування важкої глобальної оптимізації.
* **Основний вибір технології (Гібрид XFeat + LiftFeat):**
  * **XFeat (CVPR 2024):** Надшвидкий згортковий екстрактор (~5 мс на GPU). Ідеально веде прямий рух та плавні повороти.
  * **LiftFeat (ICRA 2025):** 3D-орієнтований екстрактор зі знанням нормалей поверхні. На відміну від 2D-згорток, він стійкий до сильних кутів нахилу камери до ґрунту (на розворотах втримує 518 інлаєрів проти 56 у XFeat — перевага у 9.25 разів).
* **Як працює гібрид (Dual-Rate / Adaptive Gating):**
  1. *Режим за замовчуванням (Frame-to-Frame, 60+ FPS):* На кожному кадрі працює швидкий **XFeat**. Він забезпечує мінімальну затримку (low latency) для контуру управління шасі.
  2. *Адаптивний тригер розвороту (Turn / Low-Inlier Trigger):* Якщо кутова швидкість робота зростає (поворот на місці) або кількість відстежуваних точок XFeat різко падає нижче порогу (< 100 інлаєрів), миттєво активується **LiftFeat**, який підхоплює геометрію поверхні та унеможливлює зрив одометрії.
  3. *Ключові кадри (Keyframe-to-Keyframe):* Усі ключові кадри за замовчуванням індексуються дескрипторами LiftFeat для довготривалої стійкості між-кадрової тріангуляції.
* **Мультиспектральне розширення (Multi-Modal Vision: IR & Thermal):**
  * При заміні або доповненні сенсора інфрачервоною (IR) чи тепловізійною (TIR) камерою модуль підтримує:
    * **XoFTR (CVPR 2024):** Спеціалізований трансформер для крос-модального матчингу між тепловізором (TIR) та видимим спектром (RGB). Дозволяє нічному роботові локалізуватися за денною оптичною картою.
    * **MINIMA (CVPR 2025):** Модально-інваріантний матчер нового покоління, натренований на 19 різних модальностях (RGB, NIR, TIR, SAR). Забезпечує повністю безшовний перехід між монокулярною RGB камерою та тепловізором без переналаштування геометрії.
* **Конфігурація режимів Фронтенду (Frontend Mode Selection):**
  Фронтенд реалізується через патерн фабрики (`build_tracker(mode, config)`), де користувач або система керування може динамічно обирати активний бекенд трекінгу через конфіг або CLI аргумент (`--frontend <mode>`):

  | Режим (`frontend_mode`) | Архітектура / Моделі | Призначення та сценарій використання |
  | :--- | :--- | :--- |
  | **`hybrid`** *(Default)* | **XFeat + LiftFeat** | **Основний рекомендований режим.** XFeat веде 60+ FPS прямий рух, LiftFeat підхоплює розвороти та індексує ключові кадри. |
  | **`xfeat`** | Тільки **XFeat** | **Енергоефективний / Ultra-FPS режим.** Для слабких обчислювальних платформ (Raspberry Pi 5, Jetson Orin Nano 10W) або польотів БПЛА з високою швидкістю. |
  | **`liftfeat`** | Тільки **LiftFeat** | **3D-орієнтований режим для складного ґрунту.** При частій їзді по бездоріжжю, різких нахилах шасі, вибоїнах та обертанні на місці. |
  | **`xoftr`** | **XoFTR** | **Крос-модальний режим «Ніч / Тепловізор».** Для локалізації ровера з тепловізійною камерою (TIR) за записаною вдень оптичною (RGB) картою. |
  | **`minima`** | **MINIMA** | **Універсальний мультиспектральний режим.** При встановленні мультиспектральних, NIR або комбінованих сенсорів без перенавчання карт. |
  | **`eloftr`** *(Fail-safe)* | **EfficientLoFTR** | **Аварійний безтекстурний режим.** Для суцільного снігу, піску, гладкого бруду, де звичайні точкові детектори не бачать кутів. |

### Модуль 2: Метричний геометричний кондиціонер (Metric Geometry Conditioning)

* **Що робить:** Працює асинхронно у фоні для обраних ключових кадрів. Повертає абсолютну глибину в метрах для пікселів кадру, що повністю ліквідує головну проблему монокулярного зору — дрейф масштабу.
* **Основний вибір технології:** **Metric3D v2 (ViT-Small / ViT-Large)**.
  * *Чому:* На відміну від звичайного відносного глибиноміра (MonoDepth / Depth Anything v1), Metric3D навчався з урахуванням камери з фокусною відстанню. Він відновлює метричну метрику у фізичних метрах.
* **Як працює у конвеєрі:**
  1. Коли Front-End створює ключовий кадр, його копія потрапляє у чергу Metric Engine.
  2. Модель генерує метричну карту глибини `Z(u, v)` та оцінку достовірності (variance / confidence).
  3. Для 3D точок, які відстежує трекер, витягуються їхні справжні метричні відстані.
* **Вибір провайдера глибини (Depth Provider Selection):**
  Модуль реалізує інтерфейс `BaseDepthProvider` і обирається прапорцем `--depth_mode <mode>`:

  | Режим (`depth_mode`) | Модель | Швидкість (CPU) | Особливості та сильні сторони |
  | :--- | :--- | :---: | :--- |
  | **`metric3d`** *(Default)* | **Metric3D v2 (ViT-Small)** | 1788 мс | Канонічна метрична модель. Найглибший горизонт (до 280+ м). Перевірений стандарт для UVO. |
  | **`unidepth`** | **UniDepth V2 (ViT-S/14)** | **705 мс** | **Найвища точність ближньої зони ровера (4.25 м).** Автоматично оцінює фокусну відстань лінзи K. У 2.5 рази швидша за Metric3D на CPU. |
  | **`depth_anything`** | **Depth Anything v2 Metric (Outdoor)** | 1299 мс | Лазерна чіткість меж трави, кущів та стовпів. |
  | **`road_prior`** *(Stub)* | Геометричний пріор площини | 0 мс | Інтерфейсна заглушка без активних евристик (для уникнення стрибків на вібраціях). |
  | **`hardware`** | Апаратний датчик (LiDAR / Stereo) | Залежить від сенсора | Прямий драйвер для підключення фізичних датчиків (RealSense, ZED, Livox). |

### Модуль 3: Метричний бекенд-оптимізатор (Factor Graph & Bundle Adjustment)

* **Що робить:** Об'єднує всі вимірювання (траєкторію 2D точок, метричні показання глибини, інформацію з коліс чи IMU) у спільний граф і знаходить математично оптимальну траєкторію з мінімальною сумарною похибкою.
* **Основний вибір технології (Передові рушії 2025–2026 років):**
  * **PyPose + BAE (IEEE Transactions on Robotics 2026):** «Bundle Adjustment in the Eager Mode». Працює на чистому PyTorch з нативною підтримкою груп Лі `pypose.SE3` та розрідженим прискоренням через NVIDIA cuDSS. Замінює застарілі `lietorch` та `cuda_ba` без ручних низькорівневих регістрів.
  * **Theseus (Meta AI Research):** Добре перевірена модульна диференційована бібліотека нелінійних найменших квадратів для фактор-графів у PyTorch.
* **Цільова функція оптимізації (Loss Formulation):**
  Оптимізатор мінімізує суму чотирьох факторів:
  1. *Похибка репроекції (Visual Cost):* чи збігається спроєктована 3D точка з її спостереженням на матриці камери (зважена коваріацією точок RaCo/LiftFeat).
  2. *Похибка метричного масштабу (Metric Depth Cost):* різниця між оптимізованою 3D глибиною точки та фізичними метрами від **UniDepth V2**:
     `Residual_depth = (Z_slam - Z_unidepth) / sigma_unidepth`
  3. *Плавність руху (Smooth Motion Prior):* відносна поза між сусідніми кадрами від швидкісного PnP трекера Модуля 1.
  4. *Калібр масштабу (Gauge Scale Anchor):* маргіналізація старих станів за доповненням Шура (Schur Complement) для стабільності масштабу.
* **Альтернативи на заміну (Swappable Components):**
  * *Micro-Torch Solver (Zero-deps):* Власний компактний розв'язувач на базі Levenberg-Marquardt та груп Лі (1 файл Python без зовнішніх C++ залежностей). Працює скрізь «з коробки».
  * *SymForce (Skydio):* Символьний генератор надшвидкого C++/CUDA коду оптимізації від Skydio.
  * *GTSAM / Ceres Solver:* Класичні C++ бібліотеки (вимагають копіювання пам'яті GPU -> CPU).

### Модуль 4: Замикання петель та перелокалізація (Loop Closure & VPR)

* **Що робить:** Зберігає цифрові відбитки відвіданих місць. Коли робот повертається у відому зону (навіть через тривалий час чи під іншим ракурсом), модуль знаходить відповідність, розраховує петлю і виправляє весь накопичений дрейф карти.
* **Основний вибір технології (VPR SOTA 2025–2026):**
  * **DINOv2 (ViT-S/14) + SALAD / AnyLoc:** Витягує глобальні інваріантні дескриптори (512 чисел) за ~8–10 мс. Нечутливий до зміни пори року (зелене літо -> суха осінь), хмарності, тіней і положення сонця.
  * **HNSW / FAISS:** Блискавичний пошук серед десятків тисяч ключових кадрів за < 0.5 мс.
* **Як працює у конвеєрі:**
  1. *Глобальний ембеддінг:* Кожен новий ключовий кадр кодується вектором DINOv2+SALAD і додається до просторового індексу HNSW.
  2. *Топологічний фільтр (ROVER 2026 Prior):* Відсікаються сусідні кадри за останні 45 секунд, а також фізично неможливі стрибки з огляду на історію траєкторії шасі (відсікання однакових рядів кущів/дерев).
  3. *Метрична 3D-3D верифікація (Фішка UVO):* Завдяки **UniDepth V2** обидва кадри мають готові метричні 3D-координати. Замість ненадійного 2D RANSAC проводиться **3D-3D Umeyama / Kabsch RANSAC**, що повністю виключає хибні спрацьовування.
  4. *Глобальна оптимізація поз (PGO):* Ребро замикання петлі додається до глобального графу поз `SE(3)`, і розв'язувач у PyPose/Theseus за ~20 мс виправляє всю накопичену траєкторію.
* **Крос-модальне замикання циклів (Cross-Modal Loop Closure / 24/7 Navigation):**
  * Якщо карта була побудована вдень за допомогою монокулярної RGB камери, а повернення чи патрулювання виконується вночі за допомогою тепловізора (TIR) чи IR:
    * Глобальний пошук виконується через мультиспектральні ембеддінги **AnyLoc / C-VPR**.
    * Геометрична верифікація петлі здійснюється через **XoFTR** (пряме зіставлення TIR-до-RGB) або **MINIMA** (модально-інваріантний матчинг). Це дозволяє замкнути граф і повністю усунути дрейф без необхідності повторного картографування вночі.
* **Альтернативи на заміну (Swappable Components):**
  * *MASt3R / LoMa:* Надточні 3D-арбітри для підтвердження складних геометричних петель.
  * *MegaLoc / CosPlace / NetVLAD:* Спеціалізовані нейромережі для візуальної геолокації.
  * *DBoW3:* Традиційний швидкий підхід на мішку візуальних слів (низьке навантаження на CPU, але слабкий на відкритих полях).

## 8. Апаратна конфігурація та інтерфейси сенсорів (Hardware & ROS Integration)

На основі уточненого сетапу реального наземного ровера в архітектуру закладено такі специфікації:

### 8.1. Кріплення камери на шасі: Жорстке (Rigid Mount)
* **Статичні екстринсіки (CameraExtrinsics):** Трансформація між оптичною віссю камери та рамою ровера / IMU (transform_body_cam) є строго фіксованою. Відсутні затримки реакції, люфти або коливання стабілізаційного підвісу (gimbal).
* **Прив'язка до вектора гравітації:** Оскільки камера закріплена жорстко, кути нахилу шасі (Roll і Pitch), визначені за допомогою IMU, безпосередньо фіксують оптичну вісь відносно горизонту. Це усуває накопичення кутового дрейфу за двома з трьох осей обертання.
* **Фільтрація вібрацій:** Оскільки жорстке шасі передає мікровібрації від ґрунту безпосередньо на камеру та IMU, алгоритм оптимізації використовує адаптивні коваріаційні ваги та темпоральне згладжування шуму акселерометра в ImuBuffer.

### 8.2. GNSS / GPS канал (MAVROS та автономні топіки)
* **Транспорт даних:** GNSS-пакети надходять транзитом через польотний контролер (Pixhawk / ArduPilot) по протоколу MAVLink у середовище ROS через ноду **MAVROS**.
* **Формат повідомлень:** Стандартний `sensor_msgs/NavSatFix` (за замовчуванням топік `/mavros/global_position/raw/fix`).
* **Модульна сумісність:** Модуль `uvo/core/sensors.py` містить адаптери, що приймають як об'єкти ROS-повідомлень, так і словники (dict/JSON). Це дозволяє запускати систему як у середовищі ROS 1 / ROS 2, так і повністю офлайн без встановленого ROS.
* **Метрична прив'язка (WGS84 -> ENU):** Клас `GeoCoordinateTransformer` перетворює геодезичні координати (WGS84: широта, довгота, висота) у декартові координати ENU (East-North-Up) у метрах відносно базової опорної точки маршруту.

### 8.3. IMU модуль: Універсальний модульний топік
* **Гнучкість підключення:** Підтримується отримання даних як з польотного контролера (`/mavros/imu/data` або `/mavros/imu/data_raw`), так і з окремого зовнішнього IMU-модуля через незалежний скрипт у довільний ROS-топік.
* **Клас ImuMeasurement та ImuBuffer:** Високочастотний кільцевий буфер (100–400 Гц), що синхронізує покази гіроскопа й акселерометра з мітками часу відеокадрів, обчислює початковий вектор гравітації та готує дані для преінтеграції у бекенді.
